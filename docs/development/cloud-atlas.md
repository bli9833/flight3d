# Cumulus cloud atlas (#12)

The old cloud layer used overlapping, randomly rotated dodecahedra. The replacement
uses up to 180 instanced camera-facing cards, four deterministic cumulus silhouettes,
soft alpha edges, and encoded rounded surface normals. Sun direction, sun color,
ambient light, exposure, and scene fog follow the existing atmosphere. The departure
corridor, coastal cloud altitude, and Lukla's additional 3,400m offset are preserved.
No water, terrain textures, or issue #66 behavior is changed.

## Asset provenance and budget

`src/environment/CloudLayer.js:createCloudAtlas` is the original Flight3d atlas
source. It combines seven ellipsoidal density puffs per silhouette and deterministic
sine detail, encoding a blended surface normal in RGB and coverage in alpha. There
are no third-party images, licenses, purchases, downloads, or asset-loading failure
paths. Generated bytes are held in a DataTexture and remain part of the application's
resource lifetime; `dispose()` releases its texture, geometry, material, and instance
buffers. Airport/preset changes reuse the existing layer.

The atlas is 512×128 RGBA8: 256 KiB of base pixels, approximately 341 KiB with GPU
mipmaps. Texture color space stays linear because RGB contains normal data. Gutters
and mipmaps soften distant outlines. One shared material and one instanced draw call
bound geometry and sorting work. There are 170 cards in the deterministic distribution
(340 cloud triangles). There is no separate texture transfer; the generator is bundled
with JavaScript. Alpha blending still incurs overdraw, especially looking downward.

## Cameras and transparency

Cards face the camera while preserving world up during camera roll. A fallback
basis handles an overhead camera. Normal lighting is expressed in that same basis.
Cards fade within 650m (fully invisible within 150m) to avoid a large intersecting
plane during close passes. This is a lightweight cumulus representation, not a
volumetric cloud model; silhouettes have only four variants and above-cloud views
retain billboard limitations.

`SkyAtmosphere.prepareRender(camera)` sorts cards and their atlas indices together,
back to front, immediately before `renderer.render`. This must happen before Three.js
uploads instance attributes; an object `onBeforeRender` callback runs too late for
same-frame instance-buffer updates. Sorting uses the actual camera and layer world
transform, including airport changes. Cards depth-test against opaque scene objects,
but do not write depth or cast shadows.

## Reproduce browser evidence

Use Node 22.23.2. Start the development server and a dedicated Chrome instance:

```sh
npm run dev -- --host 127.0.0.1 --port 5182
```

```sh
google-chrome-stable --headless=new \
  --user-data-dir=/tmp/flight3d-cloud-review-chrome \
  --remote-debugging-port=9458 --window-size=1280,720 \
  --use-gl=angle --use-angle=vulkan --no-first-run \
  http://127.0.0.1:5182/
```

Then run:

```sh
node scripts/verify-cloud-atlas.mjs
```

`CDP_PORT` overrides the debug port. `BASELINE_REF` defaults to `f46c426`, the
pre-change main commit. The script temporarily writes the old atmosphere module
beside the current one and removes it at process exit. It refuses to overwrite an
existing temporary baseline. It captures seven identical camera/time conditions
for each implementation (overview, near, rolled, zenith, above, sunset, night),
then cockpit, wing, and chase views in the simulator. Outputs live in
`review-artifacts/cloud-atlas/`, including screenshots and `metrics.json`.

Recorded browser evidence uses Chrome with Intel Graphics (ADL-N) through ANGLE
Vulkan at 1280×720.

The isolated comparison uses the same renderer, viewport, solar hour and camera
for both versions. Both cloud distributions use a fixed seed, but the different
algorithms consume random values differently, so individual cloud positions differ.
Five warm-up renders precede 30 timed renders, each followed by `gl.finish()`.
Reported times include CPU submission, sorting, and completion wait; they are not
GPU timer-query measurements or a full-simulator/mobile FPS benchmark. Renderer
texture/geometry counters are cumulative across both comparison scenes and environment
map loading; they must not be interpreted as per-cloud memory measurements.

Recorded cloud-plus-sky draw counts are two in both versions. Triangle counts are
124,572 before and 352 after (the sky contributes 12). Timings are very small and
noisy on this machine, so the evidence supports reduced geometry, not a claim of
higher FPS. Inspect the recorded per-view medians and p95 values rather than assuming
geometry reduction eliminates transparency cost. Browser exceptions and console
errors fail the script. Screenshots were checked for soft silhouettes, card exposure,
roll behavior, above-cloud views, sunset tint, and subdued night lighting.

Node coverage checks reproducibility, four distinct atlas silhouettes, transparent
cell edges, bounded population, the departure corridor, sorting across camera and
layer changes, tile/matrix identity, repeated airport changes, and lighting transitions.
The required gate is `npm run check`, `npm test` (247 passing), and `npm run build`.

# 인천 5단계: 근거리 차량과 전체 비행 성능

Discussion [#216](https://github.com/stlim0727/flight3d/discussions/216)의 5단계입니다.
4단계 비행 연결을 유지하면서 실제 도로의 제한된 차량, 품질/거리별 표시와
전체 비행 루프의 변경 전후 성능·로딩·메모리 증거를 추가합니다.

## 도로와 차량의 범위

고정 OSM 원본과 기존 2km 패치에서 실제 연결된 **폐회로 8개**를 추출합니다.
OSM 방향 태그와 연결 좌표를 사용하며 시각적으로 교차하는 선을 임의로 연결하지 않습니다.
일방통행의 역방향, 막다른 길에서의 U턴, 보행로·계단·자전거길, 고가·지하·비지상 layer,
출입 금지/사유 도로, 덮이거나 실내로 명시된 도로는 제외합니다.
서로 같은 도로 구간을 공유하는 회로도 제외해 중복 차량을 줄입니다.

```sh
node scripts/scenery/build-incheon-traffic.mjs
```

원본 SHA-256/바이트 수를 검사하고 `public/scenery/incheon/traffic.json`을 재생성합니다.
이 경로 데이터는 **ODbL**이며 원본과 생성 도구를 함께 제공합니다. 차량 형상은 자체 코드로
만든 단순 모형이며 외부 사진·브랜드·모델을 사용하지 않습니다. 경로는 도시 상세 구역에만 있습니다.

도로의 오른쪽 차선으로 오프셋하고 연결점은 제한된 miter로 잇습니다. 단일 방향의 좁은
도로는 중심선을 사용합니다. 4m 이하 간격으로 공통 지면 sampler를 적용하고 15%보다 큰
경사, 수면, 공항 포장, 건물 내부/벽에서 1m 미만인 경로는 제외합니다.
실제 데이터에서는 경사가 큰 회로 2개를 제외해 **회로 6개, 차량 40대**를 준비합니다.
높이는 런타임 로드 때 한 번 샘플링하며 매 프레임 원본 GIS를 파싱하지 않습니다.

차량은 각 폐회로에서 5~7m/s의 모형 속도로 이동합니다. 경로 길이와 누적 시간으로 위치를
계산하므로 루프 끝에서 다른 도로로 순간 이동하지 않습니다. 차체 방향은 앞뒤 경로 표본을
사용해 코너에서 완화합니다. 차량은 시각 효과이며 교차로 신호·양보·차량 간 충돌·항공기와의
충돌·실측 교통량·개별 라이트·개별 그림자는 포함하지 않습니다.

## 표시 비용과 상태 전이

차체·창·바퀴를 한 저상세 geometry로 합치고 최대 64대 버퍼의 **InstancedMesh 1개**를
재사용합니다. 별도 텍스처나 개별 광원을 추가하지 않습니다. 실제 준비 차량은 40대입니다.
기존 그래픽 품질을 따르며 경로의 공간 범위를 먼저 검사하고 가까운 차량만 버퍼에 채웁니다.
표시 한계 직전 80m에서 크기를 부드럽게 줄입니다.

| 그래픽 품질 | 최대 표시 수 | 카메라 거리 |
| --- | --- | --- |
| High | 64 | 1,200m |
| Balanced | 40 | 900m |
| Performance | 20 | 600m |

보이는 차량이 없으면 차량 draw call도 없습니다. 멀어진 차량은 물리/충돌 객체를 남기지
않습니다. 일시정지·인천 로비에서는 경로 시간이 멈추며 카메라 이동에 따른 거리 판정은
계속 갱신합니다. 시나리오 리셋은 위상을 초기화하고 공항을 왕복해도 버퍼를 다시 만들지 않습니다.

## 지형 높이 질의 최적화

4단계의 `getHeight`는 매 질의마다 863개 해안 꼭짓점을 순회했습니다. 바퀴·동체·카메라가
반복해서 질의하는 내륙에서 이 연산을 없앱니다. 25m 격자의 land/water 값과 해안선 선분의
경계 셀을 미리 계산하며, **경계 셀만 원래 다각형 판정을 수행**합니다.
작은 섬·구멍의 경계도 보수적으로 표시하므로 모서리 표본이 모두 같다는 이유로 무시하지 않습니다.
렌더 삼각형·해안선·접지 높이는 변경하지 않습니다. 캐시 추가 저장량은 Uint8 461,761 bytes입니다.

## 재현과 증거

```sh
npm run check
npm test
VITE_BASE_PATH=/flight3d/ npm run build
npm run preview -- --host 127.0.0.1 --port 5201 --base /flight3d/
# 병합된 4단계 ea9b54f를 별도 checkout에서 같은 base로 빌드/preview (:5202)
APP_URL=http://127.0.0.1:5201/flight3d/ BASELINE_URL=http://127.0.0.1:5202/flight3d/ \
  BASELINE_COMMIT=ea9b54febe1fd7bb4ed0d485f00e089d331cbb2e \
  chrome-session --project flight3d node scripts/verify-incheon-traffic.mjs
```

기준 빌드는 수정하지 않은 4단계이며 단순한 `traffic.enabled=false` 비교가 아닙니다.
동일 GPU/1280×720 CSS/DPR 1에서 **기준 → 변경 → 변경 → 기준(ABBA)** 순서로 측정합니다.
각 블록은 새로 로드하며 3개 품질과 활주로 조종석·접근 조종석·도시 저공 외부 시점을 검사합니다.
셰이더 준비 30프레임은 물리를 멈춘 상태에서 실행하고, 같은 시작 위치/속도로 리셋한 뒤
**실제 animate/120Hz 물리 루프를 실행**하며 native requestAnimationFrame 간격 120개를 수집합니다.
`stepSimulation()` 가속 결과나 `render+gl.finish` 시간으로 FPS를 대신하지 않습니다.
FPS 차이에 따라 통과한 비행 거리는 달라지므로 시작/종료 위치·진행 시간도 기록합니다.

평균 FPS, p95/p99, 최대 프레임 시간과 50ms 초과 수를 원본 구간 전체에서 계산합니다.
누락/빈 배열/너무 적은 표본/0/NaN/Infinity는 통과하지 못합니다.
새 장면 로딩은 HTTP 캐시를 끈 로컬 서버 요청부터 첫 도시 렌더 프레임까지 측정합니다.
OS/서버 파일 캐시는 따뜻할 수 있습니다. 긴 태스크 및 로딩 중 프레임 간격도 기록합니다.
JS heap은 측정 밖에서 GC 후 CDP로 읽고 geometry/texture 수와 함께 기록합니다.
페이지 이동 뒤 이전 컨텍스트가 남을 수 있어 CDP 절대 heap 총량 대신 로드 전후 증가분을 비교합니다.
이 수치는 실제 GPU VRAM 또는 브라우저 전체 프로세스 메모리가 아닙니다.

## 측정 결과

36개 패스에서 도시 외부 시점의 합산 평균은 기준 26.1–27.1 FPS, 변경 25.1–25.7 FPS였습니다.
p95는 약 50ms로 비슷하며 조종석은 약 8 FPS로 유지됐습니다. **전체 FPS 개선은 확인되지
않았습니다.** 차량 추가 후 도시 평균은 약 4–6% 낮고 기준 반복 자체에도 변동이 있습니다.
차량 수만큼 draw call을 추가하지 않지만 그리기와 업데이트 비용이 0이라는 뜻은 아닙니다.

초기 로딩은 기준 2486–2494ms → 변경 2001–2106ms였고, 약 1.6–1.7초의 긴 태스크는
남아 있습니다. 추가 ArrayBuffer backing storage는 약 0.483MB입니다.
[전체 수치·표본 해석·메모리 구분](../../review-artifacts/incheon-stage5/README.md).

Node 전체 검증과 기존 4단계 B737/C172 이착륙·충돌·리셋 수용 검사를 재사용했습니다.

## 남은 한계

이 장면과 한 기기의 결과를 다른 GPU/물리적 휴대폰의 FPS 보장으로 해석하지 않습니다.
3개 품질 프리셋은 같은 기기에서 비교합니다. 복잡한 조종석·그림자와 초기 지형 생성 비용은
차량 외에도 전체 프레임에 영향을 줍니다. 실제 교통 모델, 영종도 전체 확장, 추가 랜드마크,
정밀 공항 시설·등화와 인천 자동 데모는 별도 범위입니다.
